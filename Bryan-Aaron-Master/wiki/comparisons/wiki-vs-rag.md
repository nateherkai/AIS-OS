# Wiki vs RAG — Comparison

Comparison of the Karpathy LLM Wiki pattern against traditional semantic search / RAG (Retrieval-Augmented Generation). Generated by Nate Herk's Claude Code instance from Herk Brain vault data.

## Side-by-Side

| Dimension | LLM Wiki (Karpathy) | Semantic RAG |
|-----------|---------------------|--------------|
| **Retrieval method** | Reads index, follows `[[links]]` | Similarity search on embeddings |
| **Understanding** | Deeper — links encode relationships explicitly | Shallower — chunks "seem similar" |
| **Infrastructure** | Just markdown files | Embedding model + vector DB + chunking pipeline |
| **Cost** | Essentially free (tokens only) | Ongoing compute + storage |
| **Maintenance** | Run a lint; add articles | Re-embed when data changes |
| **Scale limit** | ~100s of articles (~500k words) comfortably | Scales to millions of docs |
| **Setup time** | Minutes | Hours to days |

## When to Use Wiki

- Personal or team knowledge base with hundreds of documents.
- Where relationships and reasoning matter more than raw lookup speed.
- When you want zero infrastructure overhead.
- When you're a solo operator or small team.

## When to Use RAG

- Enterprise scale — millions of documents.
- Where exact similarity retrieval is critical.
- High-throughput production systems where token costs at query time would be prohibitive.

## The Nuanced Answer

LLM Wiki doesn't kill RAG — it's a different tool. For personal AI systems, second brains, and small research projects, wiki wins on simplicity and quality. For scale, RAG or knowledge graph systems (LightRAG, etc.) remain necessary. As of April 2026, with current model context windows, wiki is underrated for the use cases it fits.
